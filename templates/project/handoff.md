- **Risk tier:** low / medium / high, because …

## In scope

Requirement IDs: R1, R2 … (the spec is the source; don't restate it here)

Out of scope:

## Constraints and failure modes

The box the work must stay inside, and the bad inputs or states it must handle.

## Must not change

Tests, API contracts, data, and behaviour that must stay exactly as they are.

## Allowed scope

Areas, services or file paths the implementer may touch. Anything else: ask first.

## Done when

Machine-checkable. At least one per requirement. Prefer checks about what the system does over checks about what the code looks like.

> If a requirement has no check you can write down, the spec isn't ready. Log it in risks and stop.

## Before you start

State your mechanism in 1–2 sentences (how you'll make the checks pass) and wait for a thumbs-up on medium and high risk work. If two requirements conflict, stop and ask; don't pick.
